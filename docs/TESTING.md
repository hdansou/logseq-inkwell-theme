# Testing a change

Three layers, cheapest first.

## 1. Structural tests: `npm test`

Run `npm run build` first whenever `src/` changed; the tests fail if a generated file is stale.

`node --test` with no dependencies. For every variant, the tests check:

- palette on `:root` and `html[data-theme="dark"]`, with dark overriding every light token, and every `--ink-*` token that `src/base.css` uses defined
- `src/base.css` free of colour literals (all colour comes from a palette)
- mapping on `html[data-theme][data-color]`
- every shui token resolving to bare HSL channels in both modes
- the full `--lx-*` scales
- `--left-sidebar-bg-color` set where core defines it
- no selectors known to be dead in DB builds (Radix, tippy, `cp__palette`, `data-bg-color`, `marker-switch`, …)
- text contrast ≥ 4.5:1 for every pair in `TEXT_PAIRS`, in both modes
- `!important` only in the allowed places
- `package.json` registering every variant in light and dark, as the build would

Every test was checked against a deliberately broken copy of the theme and fails on it.

## 2. Live check in the browser

Logseq's web app runs an in-memory DB graph ("Demo") that is safe to write to.

1. Open https://app.logseq.com and create a page with the content you changed.
2. In DevTools, inject the theme without saving it anywhere:
   ```js
   const s = document.createElement("style");
   s.id = "hs-test";
   s.textContent = `/* paste themes/inkwell-slate.css */`;
   document.head.appendChild(s);
   ```
3. Check that your selectors match (`document.querySelector(sel)`) and compare `getComputedStyle(el)` with the token you expect.
4. Repeat in dark mode (`await logseq.api.set_theme_mode('dark')`) and under another accent colour (`document.documentElement.dataset.color = 'tomato'`).

Selectors change between Logseq releases. When something doesn't apply, find the element in DevTools and confirm the class in Logseq's source before writing a selector.

## 3. Human test in the Theme-Lab graph

`npm run lab` (optionally `-- --variant <id>`) builds a DB graph with one page per UI area and a **Theme Lab — Feedback** checklist, installs the theme as the graph's `custom.css`, and opens it in Logseq-DB.app. Walk the pages in light mode, dark mode and one other accent colour. Tick each checklist item and write notes under it. `npm run lab:feedback` then saves the page to `feedback/<date>.md`.

The graph is generated by `tools/theme-lab/build_theme_lab.py` (sqlite.build EDN). The generator works around these import gotchas:

- `logseq graph import` exits 0 even when the worker rejects the EDN. `lab.sh` checks the worker log, validates the graph, and confirms `custom.css` landed.
- Only `[[uuid]]` creates a reference in a DB graph. `[[Title]]` is stored as plain text, so the generator gives every page and tag a fixed uuid and rewrites links.
- `[:build/page …]` property values aren't translated on import, so they are written as `[:block/uuid …]`.
